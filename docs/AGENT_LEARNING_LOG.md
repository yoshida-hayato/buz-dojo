## 2026-09-22 〜 09-24 まとめて復元(9/25 朝に分割投稿)

この期間の確定事項は、ブリッジの行数チェック不具合で3日間ログに入らなかった。
Slackの履歴は消える前提なので、ここへ移す。

### パッチを書くときの確定ルール

- 囲みは必ず三連バッククォート。1個だとブリッジの抽出正規表現に一致せず、
  内部ログに出るだけで Slack には何も出ない。
  「成功も失敗も報告が無い」= 囲みが壊れている、と読む。
- 三連バッククォートは、開始も終了もそれだけで1行にする。
  同じ行に中身を続けるとインラインコードと解釈され、1個に潰される。
- JSON本文にバッククォートとアスタリスクを1文字も入れない。
  cron も App Engine 構文の "every day 06:30" を使う。
- URLはスキーム直後にドメインが来ない形に分割する。
- old-string は対象ファイル内にちょうど1回だけ(grep -c で確認)。

### ブリッジの挙動として確定したこと

- JSONとして読めないメッセージは patches に入らず、patches が空だと
  save-state が呼ばれない。処理位置(ts)が進まず同じエラーが毎回再投稿される。
  止め方は、壊れたメッセージより新しい読めるパッチを1件通すこと。
- パッチは1件ずつ commit される。行数チェックが見る git diff HEAD は
  1件ごとにリセットされるので、複数出しても行数は互いに影響しない。
- 行数チェックはリポジトリ全体の差分と未追跡ファイルを数える。
  9/22-9/23 に全パッチが破棄されたのは、ワークフローの npm install が作る
  package-lock.json が未追跡の新規ファイルとして丸ごと数えられていたため。
  9/24 に社長が apply-patch.yml の Install test dependencies を直して解消。
- ブリッジは .github/ 配下を変更できる。変更できないのは scripts/bridge/ だけ。
- main への push でテスト通過後に本番へ自動デプロイが走る。
- ブリッジの実行がSlackに現れた実時刻は 14:33 / 21:10 (9/22)、15:21 (9/24)。
  ドキュメント上の cron と一致しないので、結果は Slack 上の実時刻で見る。

### この環境の制約として確定したこと

- GitHub への push / PR / API 呼び出しは403で必ず失敗する。試さない。
- npm registry がプロキシに遮断され jest を取得できない(403)。
  手元で npm test は実行できない。検証できるのは node --check と差分行数まで。
  「テストが通る見込み」を断定しないこと。
- Slack への投稿は社長本人のアカウント権限で送られる。表示名は必ず吉田隼人になり、
  末尾の署名だけが機械投稿の目印。ブリッジは別アプリで正しく分離している。
- 巡回セッションからの Slack チャンネル自動作成は、セッションの安全装置に
  外部システムへの書き込みとして拒否される(9/24 に2回確認)。
- この巡回タスクは #buz-dojo-agent しか読まない。他チャンネルを見るには
  タスク設定画面でのプロンプト編集が必要。エージェント側の update trigger では
  反映されない(3回失敗、社長が設定画面から直した時だけ反映された)。
- Claude のメモリ機能はあるが対象は Claude 自身の会話で、Slack の中身は含まない。
  過去を全部遡れる状態を作る手段は、このログ + キャンバス + Slack検索を厚くすること。

### 社長の判断・方針(確定)

- 投稿者名は現状のまま(社長アカウント名 + 末尾の Claude 署名)でよい。9/24 承認。
- チャンネルは今後エージェントが作る方針。ただし安全装置により現状は作れない。
- 全チャンネルを監視してほしいとの要望あり。実現にはタスク設定画面の編集が必要。
- 最終目標は自律型エージェント。過去のやりとりを遡れることを重視している。
- Slack の履歴は消える前提で、記録は GitHub 側に残す。

### 外した判断(次に同じ穴に落ちないために)

### パッチ投稿の手順(毎回これを機械的に実行する)

6. 長い内容は意味の切れ目で分割する。ブリッジは ts の古い順に処理するので

## 2026-09-28 夜シフト

### 確定(新規・最重要): SlackのMCP送信ツールは本文をMarkdown変換する。h1からh6は repo に届かない

今朝の3件(ガイドページ・title/description・フッターリンク)は、ブリッジが復旧しても100パーセント適用されない状態だった。原因は3つ重なっていた。

1. 囲みがシングルのバッククォートになっていた。ブリッジの抽出は三連を要求するので、ログに出すだけで Slack には何も投稿せず静かに消える
2. フッターパッチの old_string のインデントが1スペースで、実ファイル(2スペースと4スペース)と一致せず出現回数0
3. 新規HTMLの見出しが h1 タグではなく Markdown の記法になっていた。ブラウザでは井桁がそのまま文字として出る

機構(検証で確定): slack_send_message は message を Markdown として解釈し直して送る。そのため

- 囲みを PATCH_V1 の次行に三連で置き、JSONを同じ行に続けると、囲みがシングルに潰れる。囲みだけの行にして、JSONを次の行から始めると三連のまま保存される
- 本文に HTML タグが含まれると HTML から Markdown への変換が走る。h1 から h6 は井桁記法に置換され、閉じタグ単独は削除される。連続スペースは1個に潰れる
- p, ul, li, a, strong, div, nav, article は素通りする。div に role=heading と aria-level を付けた形も素通りする
- ユニコードエスケープでの回避は不可。バックスラッシュが二重化されて json.loads が別物を返す

つまり今朝の3件は、書いた側の不注意ではなく送信経路の仕様だった。ローカルで json.loads が通ることも、送信前に文字数を数えることも、この事故を検出しない。

### 新しい必須手順: 投稿したら読み直して、読み直した方で検証する

送信した本文と保存された本文は別物になりうる。今夜からは、パッチを投稿したあと slack_read_channel で読み直し、読み直した本文を clone に当てて、狙った結果になることを確認する。ローカルで作ったJSONを検証するだけでは足りない。

### 今夜出したもの(4件・すべて読み直して検証済み)

1. css/legal.css に legal-h1 と legal-h2 のクラスを追加。既存の h1 と h2 のセレクタに並べただけで宣言は変えていない
2. guides/seisan-kanri-2kyu.html を新規作成(90行)。見出しは div の role=heading と aria-level
3. index.html の title と meta description
4. index.html のフッターにガイドへのリンク

4件を順に当てて、置換対象はいずれも出現回数1、リポジトリ全体の変更行数は102行(上限200)。テストは functions と Firestore ルールだけなので、この4件は担保されていない。

### 制約の訂正: 1メッセージは5000文字まで

slack_send_message は1テキストあたり5000文字。それを超えると no_text エラーで送信自体が失敗する。ガイドページのJSONが5125文字で最初に弾かれた。長いファイルは本文を削るか分割する必要がある。

- Musk 2026-07-29「1年以上前からペナルティは無い」、
  Bier 2026-07-28「もうリンクを返信に置く必要はない」

### 確定: 相互ロックは組めない。ブリッジが1件ずつテストするから

「payment なら買い切り文面が必要」と「subscription なら買い切り文面は禁止」を
両方入れると、文面を先に出しても宣言を先に出しても必ずどちらかのテストに落ちる。
ブリッジは1パッチごとにテストするので、複数ファイルを原子的に入れる手段が無い。
相互ロックは移行そのものを不可能にする。

解は、ロックを増やすことではなく切替点を1ファイルに集約すること。
法務文面・画面表記・決済モードのすべてを config/pricing.js の CHECKOUT-MODE から
実行時に読ませれば、切替は1ファイル1パッチになり中間状態が存在しなくなった。

教訓: 順序の問題を順序の規則で解こうとすると規則が増える。
切替点を1つに減らすほうが、規則より強い。
