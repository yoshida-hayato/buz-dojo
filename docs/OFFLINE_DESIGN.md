## 前提 (すべて repo の実測)

- 問題データは別オリジンに在る。subjects/registry.js の contentBase は
  sap-dojo と gakusyu-dojo の公開 URL で、fetch は mode cors
- 問題データは元から全文がブラウザに落ちている。js/subject-loader.js が
  questions.js を loadScript で丸ごと読む。1科目で数MB
- 版クエリは実行時に決まる。resolveCacheBust が contentVersionUrl を
  cache no-store で取り、失敗すると APP_VERSION に落ちる
- 購読状態は 10/18 10:48便 から localStorage に控えが在る (uid ごと・30日)。
  圏外でもパック購入者をパック購入者として扱える

## 決めたこと

### 1. 控えの入れ物は2種類に分ける

| 名前 | 中身 | 版が上がったとき |
| --- | --- | --- |
| bizdojo-app- に版を足した名前 | 配信物 (html/js/css) | 消す |
| bizdojo-offline- に科目IDを足した名前 | その科目の問題データ | 残す |

js/app-chrome.js の OFFLINE_CACHE_PREFIX が後者の接頭辞で、
clearAppCaches はこの接頭辞で始まる入れ物を消さない。
2026-10-18 18:48便 にこの分岐だけ先に入れた。Service Worker がまだ無いので
Cache Storage は空で、今日の動きは1ミリも変わらない。
先に入れたのは、後から SW を置いた日に、版を上げるたび利用者が数MBを
取り直す形になっていることに気づく、という順番を避けるため。

### 2. 版クエリは、控えるときに解決した版で引く

圏外では resolveCacheBust が落ちて APP_VERSION になるので、控えた時の
版クエリと探す URL が食い違う。SW の既定の突き合わせは完全一致なので、
控えが在っても当たらない。だから問題データの控えは ignoreSearch を true に
して引く。問題データの URL は科目IDごとに1本で、クエリは版しか乗って
いないため、取り違えは起きない。

### 3. 消す道を必ず用意する

端末に数十MB (10科目ぶん) を置く以上、利用者が消せること。
マイページに「オフラインの控えを削除」を1つ置く。
