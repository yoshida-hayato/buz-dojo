# エージェント業務プロンプト 変更提案と反映履歴

プロンプト本文の正本は docs/AGENT_PROMPT.md。このファイルはその差分の申請書と台帳。
2026-09-29 に社長から「プロンプトを変更したくなったら書類にまとめておいてくれれば変えておく」
との指示を受けて作成。以後ずっとこの経路で更新する。

## 手順(エージェント側)

1. この docs/AGENT_PROMPT_PROPOSALS.md に提案を append で足す。
   書くのは4つだけ: 何を変えるか / なぜ(観測した事実) / 置換前の文面 / 置換後の文面。
2. docs/AGENT_PROMPT.md の該当箇所を PATCH_V1 の置換で直す。
   このとき本文の末尾に何も足さない。社長は「ここから本文」以降を末尾までコピーするので、
   本文の後ろに付録を置くと一緒に貼られてしまう。追記したい情報は本文の中の該当節に入れる。
3. Slack に1行で伝える。「プロンプトの更新提案: (要点)。docs/AGENT_PROMPT.md を貼り替えてください」
4. 社長が貼り替えたと分かったら、AGENT_PROMPT.md 冒頭の反映状況と版を書き換え、
   この台帳の該当提案に反映日を入れる。

## 手順(社長側)

docs/AGENT_PROMPT.md を開き、「ここから本文」の行より下を末尾までコピーして、
スケジュールタスクのプロンプト欄に貼り替える。それだけで完了。
貼り替えたらSlackに「プロンプト反映した」と1行ください。台帳に反映日を書きます。

## 注意: 反映されるまではファイルは効かない

このリポジトリを直しても、あなた(次の私)に実際に渡される本文は変わらない。
渡された本文と docs/AGENT_PROMPT.md が食い違っていたら、
渡された本文が現に効いているほうで、ファイル側は提案。勝手に「もう変わっている」と思わないこと。

### 提案001: 出社したら前便のパッチが main に入ったか確かめる(未反映)

何を変えるか: 「出社したら、まず記憶を取り戻す」に4番目として、
前便で出したパッチが main に入ったかを git log で確かめる、を足す。

なぜ: 2026-09-29 11:49 JST 時点で、今日出した 07:56 / 08:56 / 08:57 / 10:01-10:03 / 10:58-10:59 の
パッチは main に1件も入っていない(auto: で始まる最後のコミットは 9/29 07:00 JST)。
9/24-9/28 の5日間の停止も、外から見えるのは同じ「無音」だった。
無音を早く見つける唯一の計器が git log なので、記憶を取り戻す手順に入れたい。
入れなくても毎回やればよいが、まっさらで起動する以上、手順に書いていないことは抜ける。

置換前: 3. Slackの直近30件 — buz-dojo-agent (channel_id: C0C34F5M1QV) を読む。
置換後: 同じ行のあとに 4. として「前便のパッチが main に入ったかを git log --oneline -10 で確かめる。
auto: で始まるコミットが前便の分まで来ていなければ、ブリッジが止まっているか全件破棄されている。
その場合はSlackのブリッジ発言を探し、無ければ止まっていると判断する」を足す。

### 提案002: 記憶の入口を1枚にする(2026-10-17 03:48便 / 未反映)

何を変えるか: 「出社したら、まず記憶を取り戻す」の手順1から3を、
docs/AGENT_HANDOVER.md を読む → 学習ログは末尾200行だけ → git log →
Slack直近20件、の4つに置き換える。あわせて「学んだことは残す」節に、
便の終わりに引き継ぎメモを書き替えること、ログへの追記は30行以内、を足す。

なぜ: 手順が物理的に実行できなくなった。10/17 03:48便の実測で、
学習ログは628KB・9,515行・117便ぶん、キャンバスは434,034文字。
この便ではキャンバスの読み取りと Slack直近30件の読み取りが、どちらも
「大きすぎる」として拒否され、中身はファイルに落とされた。手順どおりに
読もうとすると、1手も打たないうちに出社が終わる。
記憶の総量は1便あたり約7KB増え、毎時出社なら1日約167KB増える。
放っておけば、来週には末尾の追記すら危うくなる。

歴史(なぜそう決めたか)と現在(いまどうなっているか)を同じファイルに
混ぜたのが原因である。歴史は append で増え続けてよいが、入口は
1枚に収まって上書きされる形でないと、毎便の固定費になる。

置換前: 現行の「## 出社したら、まず記憶を取り戻す(順番に3つ)」から
「チャンネルは流れて消えますが、このファイルは残ります。」までの全文。
置換後: 同じ便のパッチで docs/AGENT_PROMPT.md に反映済み。そちらを読むこと。

## 2026-10-18 13:48便: ブリッジの制限が緩和されたので、該当の1段落を差し替える

なぜ: 社長が「いつもAIがここを気にしているので」と言って、同日のうちに
3箇所を直した。実測で main の先端を確認済み。

- .github/workflows/apply_patch.yml の cron が 17 毎2時間 から 17 毎時 に
- 同ファイルの MAX_PATCHES_PER_RUN が 15 から 50 に
- scripts/bridge/apply_patch.py の conversations.history の limit が 50 から 300 に

本文の数字3つが全部古くなった。それだけなら数字の差し替えで済むが、
社長の指摘の本体は数字ではない。「毎便 未適用を数え直す」「進んでいない
時間からブリッジの生死を判断する」という振る舞いを、本文が誘発していた。
直近50件という窓があったから、あふれる心配を毎便させる必要があった。
窓が300件・毎時・50件になったいま、その心配はほぼ成立しない。
数字だけ直して不安の作法を残すと、社長が消したかったものが残る。

置換前: 現行の「GitHub Actions が2時間ごと(JST の奇数時: ...)」で始まる1段落。

置換後: 同じ便のパッチで docs/AGENT_PROMPT.md に反映済み。そちらを読むこと。
要点は、数字を 毎時 / 50件 / 300件 に直したうえで、件数を数え直す義務と
時間から生死を判断する癖を明示的に外し、急ぎの依頼の前に直前の枠の成否を
見ることだけを残した。

## 2026-10-18: 出社を6時間ごとにし、1便を深くする (v3 から v4)

なぜ: 社長の指示。「毎時やっているのを6時間に1回にして、1回の思考や
行動量をその分今の10倍くらいにしてほしい」。

頻度だけ変えると、1日の産出が6分の1になる。実際この日の毎時便は、
1手打って終わり、測り直しは次の便、取りこぼしの始末はさらに次の便、
という形が続いていた。07:48便 は 03:48便 の取りこぼし (壁の文面3箇所の
うち1箇所しか直っていない) を4時間後に見つけている。1便が短いことが
原因で、分割された仕事の継ぎ目に穴ができていた。

だから本文の変更は7箇所に分かれる。

1. 冒頭の出社頻度を 1日4回・6時間ごと (JST 00:48 / 06:48 / 12:48 / 18:48) に
2. 新しい節「1回の出社の使い方」を 職責 と 記憶を取り戻す の間に足す。
   1便の形を 観測 → 直す → 測り直す → ガード → 取りこぼしを grep で全部閉じる
   と定義し、ここまでで1件と数える。余力があれば3主題まで。
   サブエージェントの並行利用、ローカルでの描画計測、1便10〜20件のパッチ、
   同じ便の後半での自己検証 (ブリッジは毎時17分なので、便の前半に出した
   パッチは同じ便で main に入ったか確かめられる) を明示する
3. 学習ログの読み取りを末尾200行から400行へ
4. Slack の読み取りを20件から30件へ。拒否されても中身はファイルに落ちる
5. 学習ログの追記上限を30行から80行へ (1日では 720行 から 320行 に減る)
6. 仕事の仕方の「1回の出社で取り組むのは1件だけ」を「深さを優先する」へ
7. ブリッジの段落を、1便10〜20件・報告は1便1通 の前提に合わせる

反映: この日はエージェントが Claude Code Remote の update trigger で
タスク設定の cron と本文を直接書き替えた (社長が指示したため)。
cron は CRON_TZ Asia/Tokyo 48 0,6,12,18 で、次回は 18:48 JST。
ただし本文の「プロンプト自体を変えたいとき」の節は変えていない。
エージェントが自分の判断で自分のプロンプトを書き替える形にはせず、
提案を出して社長が決める流れを残した。社長が明示的に指示したときだけ
直接反映する。
