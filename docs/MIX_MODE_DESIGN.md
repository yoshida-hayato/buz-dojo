## いちばん大きい塞ぎ: 成績の書き先が1本しか無い

QuizStorage は「いま開いている科目」を1つだけ持つ (js/storage.js の
useSubject が this.subjectId と this.KEY と this.stats を差し替える)。
record(questionId, ...) はその1本に書く。Entitlement.recordAnswer も
引数で渡された科目の1日20問に数える。呼び元は CURRENT_SUBJECT.id である。

だからミックス中に科目をまたいで出題すると、全部の答えが、たまたま開いて
いた1科目の成績に積まれる。段位も習得数も分野別も、12科目ぶんが1科目に
流れ込む。これは画面の不具合ではなく、利用者の成績データが壊れる形である。

しかも useSubject は非同期である (cloud から読み直す)。1問ごとに呼び替える
形は取れない。

この repo には既に _scrubPollutedStats と _looksLikeSapPollution が在る。
つまり「科目をまたいで成績が混ざる」事故は過去に起きていて、その後始末の
仕掛けが残っている。ミックスは、その事故を仕様として持ち込むことになる。
ここを設計せずに画面だけ作ってはいけない。

## 設計 (次に取る人へ)

鍵は2つある。

1. 問題 id から科目が引ける。QuestionStatsPaths.guessSubjectId(questionId)
   が接頭の表で当てる (ap-kamoku-b の apb- まで13本そろっている)。
   だから「いま開いている科目」ではなく「その問題の科目」で書き先を決められる
2. 書く入口は2行しか無い。だから直す範囲は小さい

手順は3段に分ける。1段ずつ別の便で出し、段ごとに見張りを置くこと。

### 第1段: 書き先を問題から決める (ミックスの画面は作らない)

- QuizStorage に、いま開いている科目を差し替えずに、別の科目の控えへ1件
  書く口を足す (writeTo(subjectId, questionId, isCorrect, isInput) の形)。
  cloud の読み直しを伴わないこと
- quiz-engine の2行を、CURRENT_SUBJECT.id ではなく「その問題が属する科目」
  に向ける。ただし接頭からの当て推量に頼らないこと (下の 訂正 を読む)
- 見張り: 通常の出題で、2つの引き方が全科目で一致すること。
  一致しない問題 id が1つでも在れば落とす。これが土台である

訂正 (2026-11-08 18:48便 に実測): 第1段を guessSubjectId(questionId) だけで
組んではいけない。測った事実は4つである。

- 接頭の表に当たらない id は、既定の科目 (sap) に行く。これは意図された
  振る舞いで、既存の見張りが字面で固定している
- SAP のマスタの問題 id は t- と mm- で、接頭を1つも持たない
  (本番の data を取得の口で読んで実測)。つまり SAP は既定であることだけに
  頼っている
- 接頭の表から ws- (windows-shortcuts) の行を外しても、テストは1059件とも
  通る。マスタが外に在る10科目には、接頭の食い違いを捕まえる所が無い
  (この便で、表に漏れが無いかだけを見る1件を足した)
- いまの本番の書き込みは、既に科目を明示で渡している。quiz-engine が
  statsMeta に CURRENT_SUBJECT.id を入れ、question-stats がそれを
  guessSubjectId の第2引数 (hint) に渡す。当て推量は hint が無いときの
  控えでしかない

だから安全な形はこうである。ミックスの出題プールを作る側は、どの科目の
データから読んだ問題かを必ず知っている。その科目 id を問題に添えて持ち回し、
書き込みの時に hint として渡す。接頭は控えのまま残す。

こうしないと、接頭が1つ欠けるか食い違った科目の成績が、黙って sap の控えへ
流れ込む。repo に _scrubPollutedStats と _looksLikeSapPollution が残って
いるのは、同じ事故が過去に起きたからである。仕様として持ち込まないこと。

なお QuizStorage.record は100行を超えるので、1件200行のパッチでは
1手で書き替えられない。緩める、直す、締め直す の3波に分けること。

### 第2段: 読む側をミックスに耐える形にする (2026-11-09 06:48便 に半分閉じた)

閉じた側。誤答と解説を引く母集団を決める場所を js/quiz-builder.js の
entryPool 1つに寄せ、buildQuestion が第4引数で母集団を受ける形にした。
quiz-engine は slot.pool をそれに渡し、組んだ問題にも持たせる。
見張りは mix-distractor-pool (8件、12通りに壊して12通りとも落ちた)。

なぜ要ったか (実測)。buildQuestion は、自前の肢を持たない問題の誤答を
母集団から「同じ category の別の問題」を引いて作る。QUIZ_DATA を本物の
ap-kamoku-b (100問) にしたまま SAP の tcode の問題を組むと、ap-kamoku-b に
tcode が1件も無いので誤答が0件になり、肢が1つ (正解だけ) の問題が出る。
例外は出ない。利用者は必ず正解し、2回続けば習得が黙って進む。
大域を素で読んでいたのは5箇所だった (誤答の候補、必ず混ぜる誤答、
Tコードの索引、用語の誤答解説、ショートカットのトークン集め)。
5箇所とも母集団から引く形にそろえ、見張りが「entryPool 以外で QUIZ_DATA を
読む行が在れば落ちる」ところまで閉じた。本番の動きは変わらない
(3科目246問で、乱数を固定して直す前と後の肢を突き合わせ、1文字も違わない)。

### 第3段: 画面と、読み込む量の制御

画面を出す前に閉じることとして書いていた1件は、2026-11-14 18:48便 で閉じた。

壊れ方。ミックスで2科目の成績が並んで伸びると、累計と正解と習得の3つが
完全に一致する瞬間が出る。そのとき既存の「科目間成績コピー混入」の検出が
発火し、片方の科目の成績が丸ごと空に戻る。検出は数だけを見て問題 id を
見ていなかった。写しは問題 id まで同じになり、混ぜた結果は1件も重ならない。

閉じ方。_pairIndicatesCopyPollution に門を1つ入れた。問題 id が1件も
重ならず、かつ累計が自分の q で説明できるなら写しとみなさない。2つめの
条件が要るのは、累計だけが他科目のものに膨らむ事故 (q は自分のぶんしか
無い形) が在り、そちらは id が重ならないからである。どちらかが読めない
ときは否定しない。つまり検出は従来どおり効く側に倒れる。

本番で検出が走る口は2つ在った。一括判定 (_looksLikeCrossSubjectPollution)
と、科目一覧や成績の画面が問題マスタを読んだ後に呼ぶ reconcileForSubject
である。後者は累計だけの写し (before) を渡していたので q が見えず、
門を入れただけでは閉じなかった。400問が0問になるのを実測して気づいた。
1箇所目だけ直して終わらせないこと。

測った数字。問題 id が別の2科目は、直す前は130問から900問のどの量でも
1科目が消え、直した後は0科目である。本当の写し (問題 id まで同じ) と
累計だけの写しは、直す前も後も消える。ふつうの利用者の成績は17通りの形で
直す前と1バイトも違わない。約束は mix-pollution-id-overlap、壊し方の
確かめは mix-pollution-id-overlap-break、保守側の枝の記録は
mix-stats-pollution-risk に在る。

- 選べる科目の一覧 (既定は全部入り、外す印を付けられる) を置く。
  社長の「科目は選択で消したりもできるように」はここ
- 読み込む量が問題である。全科目を素で読むと8MB前後になるので、
  ミックスの開始時に全部読むのはやらない。取れる手は2つ:
  (a) 選ばれた科目を順に読み、読み終わった科目から出題に混ぜる
  (b) 科目ごとに「出題に使う分だけ」を先に読む形をマスタ側に作ってもらう
  (b) はよその repo の持ち主 (社長) の手が要るので、まず (a) で測ること

- (a) の前提は 2026-11-15 に閉じた。それまで、科目を読む口は loadSubject
  1つしか無く、1本読むたびに SUBJECT と QUIZ_DATA と CHANGELOG と
  選択中の科目 と loadedId の5つを動かしていた (実測)。つまり (a) の
  「順に読む」をそのまま書くと、12科目を読み終えた時点で利用者が選んで
  いた科目が最後の1本に置き換わり、次に開いたとき覚えの無い科目が開く。
  しかも大域は1科目ぶんしか置けないので、読んだ先から前の科目が消える。
  閉じ方は2つ。loadQuizBundle を、取得と評価だけをする fetchQuizBundle と、
  それを大域に載せる薄い包みに割った (第2段の buildPool と同じ形)。
  そのうえで loadSubjectData を足した。subject.js と問題データを取って
  束を返すだけで、大域にも localStorage にも1つも書かない。
  評価は既存の evalDataScript を通すので、頁を評価しうる箇所は増えていない。
  測った数字。本番の loadSubject は3科目とも、直す前と立つ大域も
  選択中の科目も loadedId も返り値も1バイトも違わない。
  loadSubjectData を2本続けて呼ぶと、見張る14個が0個しか動かず、
  fe-kamoku-a 46問を開いたまま fe-kamoku-b 100問と ap-kamoku-b 100問を
  同時に手元に持てる (計246問)。直す前は1科目ぶんしか持てない。
  見張りは mix-subject-data-read (7件) と mix-subject-data-gate (6件)。
  8通りに壊して8通りとも落ち、直す前の subject-loader.js では
  13件中11件が落ちる (変化の両側で通る試験ではない。失敗の型21)

- 出題枠を組む側は 2026-11-15 に閉じた。buildMixedPoolFrom (js/settings-ui.js)
  が、科目ごとの集合を受けて buildPoolFrom を科目ごとに呼び、出てきた枠に
  subjectId と母集団を押す。quiz-engine は 第1段 と 第2段 で入れた口で
  slot.subjectId と slot.pool を既に読むので、呼び元ができた時点で
  成績の宛先も誤答の母集団も科目ごとに正しくなる。呼び元はまだ無い。
  なぜ絞りを科目ごとに通すか (実測)。開いている科目の優先度の絞りを
  3科目に素で当てると、246枠が 21枠から246枠 の幅で揺れる。いちばん悪い
  場合 (優先度3だけ) は225枠が黙って消える。分野も同じで、どの科目も
  持たない分野を渡すと素では0枠になる。だから科目ごとに、その科目が
  現に持つ分野と優先度を全部通す。解答方式は選択式に固定し、モジュールの
  絞りは切る (チップは開いている科目のものなので他科目に当たらない)。
  母集団が効いていることも測った。この repo の3科目は全問が自前の肢を
  持つので、渡しても渡さなくても肢は4つで変わらない (246問で実測)。
  効くのは自前の肢を持たない形 (SAP の用語) で、同じ形の2科目を作って
  測ったら、渡さない場合は相手の科目の語が30問とも肢に混ざり、渡すと
  0問になる。見張りは mix-pool-build / mix-pool-shape / mix-pool-gates /
  mix-pool-distractors (17件)。13通りに壊して13通りとも落ちる。
  門を3つ消したことも書いておく。記述式のカテゴリを空にする門、枠の
  forceInputMode を偽で潰す門、hasModuleInputs を偽にする門は、
  どれも外しても結果が1件も動かなかった (先に効く4行が在るため)。
  動かない門は、次の人が要らないと読んで本物のほうを消す筋になる。

- 残っているのは画面だけである。要るのは3つ。科目を選ぶ一覧 (既定は
  全部入り、外す印を付けられる)、選ばれた科目を順に読む進み具合の表示、
  そして無料20問の枠の足し算である。枠は現に課金が動いている境目なので、
  画面と同じ便で、前と後を数字で示して出すこと。

- 出題の絞りに要る集合も 2026-11-15 に閉じた。buildMixedPoolFrom は科目ごとに
  習得済み・間違えた・解いた の集合を要るが、4つの一覧 (wrongIds /
  answeredIds / choiceMasteredIds / inputMasteredIds) は this.stats.q しか
  見ないので、開いている1科目ぶんしか作れなかった。useSubject で切り替える
  手は取れない (非同期でクラウドを読み直すうえ、開いている科目が動く)。
  規則の正本を QuizStorage._selectionSetsFrom 1つに寄せ、端末の控えから
  他科目の q を読む selectionSetsFor(subjectId) を足した。4つの一覧は
  その包みになり、stats.q を直に走査する所は repo 全体で0件になった。
  返る4つの名前は buildPoolFrom が読む欄と同じなので、画面はこれを
  そのまま科目ごとの集合に渡せる。
  測った数字。40通りの成績 (欄が欠けた形を含む) で、4つの一覧とも直す前と
  顔ぶれが1件も違わない。見張りは mix-peer-selection-sets (7件) で、
  10通りに壊して10通りとも落ち、直す前の storage.js では7件とも落ちる。
  混入検出はここでは走らせていない (あれは控えを読み込むときの手当で、
  出題の絞りに当てると同じ成績を二度判定することになる)。

- まだ測っていないのは、よそに在る10科目の実際の大きさである。
  8MB は、この repo の3科目の1問あたりの字数から出した見積りで、
  手元の Chromium は外のホストに出られないので直には測れない。
  画面を作る便は、まず読む順と上限 (何科目ぶんで止めるか) を決めること
- 有料科目の扱いを決めてから画面を出すこと。権利の無い有料科目を
  ミックスに混ぜると、1日20問の壁が科目ごとに別々に来るので、
  途中で「この問題は出せません」が混ざる。いちばん素直なのは、
  ミックスの対象を「権利が在る科目 + 無料科目」に限り、
  外れた科目は一覧に鍵つきで見せることである

## やらないと決めたこと

- 1問ごとに QuizStorage.useSubject を呼び替える形。非同期であり、
  cloud の読み直しが1問ごとに走る。測らなくても筋が悪い
- ミックス専用の成績の控えを新しく作る形。科目別の成績と二重になり、
  段位と習得数の正本がどちらか分からなくなる。書き先は既存の科目別のまま、
  宛先の決め方だけを変える
